# WordPress R2 Backup

WordPressのファイルとDB（データベース）をage公開鍵で暗号化し、Cloudflare R2へ保存するプラグインです。元サイトのファイルや索引が失われても、保存先の暗号文と対応する秘密鍵から独立復旧キットを使えます。

## 主な機能

- 手動バックアップと毎時・毎日・毎週の定期バックアップ。
- 保守あり／保守なしの取得、工程別の進捗と所要時間の表示。
- 完全保存、フォーム送信情報の除外、テーブル・フィールド・ファイル・設定行の個別指定。
- パック単位の暗号化、世代間の同一内容の再利用、R2保存物の全内容照合。
- 保存期限と世代指定の削除。別世代が参照する共有暗号文は保持。
- WordPress管理画面と独立PHPの復元入口、標準MySQL／MariaDBと簡易SQLiteの復旧経路。

新しい取得は目録v4です。旧v1・v2・v3の復旧経路も維持しています。バックアップの完了と、サイトとして復旧できることの確認は別です。

## 導入

[GitHub Releases](https://github.com/kamihicouki/wordpress-r2-backup/releases)からプラグインのZIPを取得します。`SHA256SUMS`と照合してから、WordPress管理画面の「プラグイン → 新規プラグインを追加 → プラグインのアップロード」でZIPを指定してください。配布ZIPには本番用PHP依存物と、対応環境用のage（公開鍵暗号化ツール）が含まれます。

ソースから導入するときは、WordPressの`wp-content/plugins/wordpress-r2-backup`へ配置し、プラグインのルートで本番用依存物を構築します。

```sh
composer install --no-dev --no-scripts --no-plugins --prefer-dist
```

WordPress管理画面でプラグインを有効にし、専用の非公開R2バケット・バケット用キー・異なるage公開鍵2本を設定します。秘密鍵はサイト外に分けて保管し、両方の公開鍵で確認用データを復号できることを確認してください。復旧キットの作成と接続ファイルの扱いは[独立復旧の手順](recovery/README.md)を参照してください。

## 開発元と公開リポジトリ

汎用機能の開発と修正は、このGitHubリポジトリでプルリクエストを開き、レビューと検証を経て `main` に取り込みます。正式配布は、検証した `main` のコミットにタグを付けてGitHub Releasesから行います。各サイトへの取り込みと配備は、サイトごとの手順で行います。`PUBLICATION.json` は最初にソースを公開した時点の出典とファイル照合値を記録しています。

## 管理画面と設定

左メニューの **R2 Backup** に、バックアップ、復元、ストレージ設定、保存範囲と除外設定、保存期間と容量があります。保存範囲はR2接続前にも設定でき、初回の接続設定へ引き継ぎます。

ストレージ設定には、CloudflareアカウントID、専用バケット、バケット専用のR2アクセスキー、異なるage公開鍵2本を登録します。ageは公開鍵でファイルを暗号化するツールです。Cloudflare全体のAPIトークンは使いません。OAuth（Cloudflareへログインして接続を許可する方式）は未実装です。

秘密アクセスキーはサイトの認証設定で暗号化し、画面へ再表示しません。サイトの認証用salt（暗号化に使うサイト固有の設定）を変更した場合は、接続設定を再登録します。復号用秘密鍵はバックアップ設定に入力せず、取得対象外の別々の場所に保管します。

バックアップ開始前には、公開画像の登録と保存元の実ファイルを参考検査できます。検査は除外設定の適用前の確認であり、外部画像を取得したり元データを変更したりしません。登録された画像でも保存元に実ファイルがなければ保存できず、記事内だけの参照・外部URL・個別除外による不足を網羅する保証もありません。

### 保存範囲と任意除外

プリセット（設定のひな型）は次の3種類です。

- **完全保存**は、保存範囲内のファイルとDBを除外・値の加工なしで保存します。`wp-config.php`、認証設定、WordPressユーザー、フォーム送信情報も含みます。
- **フォーム送信情報を除外**は、確認できた問い合わせ・申込の送信データ、添付、送信記録を除外します。フォーム定義、WordPressユーザー、システム設定は保持します。未知のプラグインの送信情報を網羅して検出する保証はありません。
- **カスタム**は、分類と個別ルールを使います。テーブル、フィールド、ファイル・フォルダー、`option_name`で選ぶ設定行、値の完全一致で選ぶ行を指定できます。SQL（DBの操作文）や設定の秘密値は入力しません。

新規設定の初期値は完全保存です。以前の設定は、旧来の固定除外も含めて「カスタム（以前の設定を継承）」へ移します。継承中の内容は画面に表示します。新しい明示的な「含める」は対応する旧除外や分類より優先し、「継承」に戻すと以前の設定が再び有効になります。

完全保存を選んで保存すると、任意除外、個別指定、以前の互換ルールをすべて解除します。過去の世代で除外された内容は復活しません。旧設定の継承中は保存元を従来のWordPressルートに保ち、新しい追加ルートを自動では加えません。

行と設定名の指定はテーブル指定より、テーブル指定は分類より優先します。ファイル・フォルダーの明示指定も分類より優先します。フィールドの「含める」だけでは、除外された行全体は復活しません。テーブルのデータを除外しても構造は保持します。

新しい設定では、未知の名前やメールらしい文字列を理由に勝手に除外しません。旧設定を継承した対象では、以前の未確認候補による停止も維持します。新しいフィールド除外でNULL（値がない状態）を安全に使えない場合は停止します。根拠なく`removed-N`や`0`へ置換しません。旧設定の置換動作は互換性のために保持します。

### 完全保存でも必要な安全条件

完全保存の範囲は、WordPress本体と構成上必要なファイルルート、および接続先の1つのDBです。親ディレクトリの`wp-config.php`、別の場所にあるコンテンツやメディアは、WordPressの設定から追加ルートとして記録します。OS全体の複製ではありません。

処理用領域、索引、秘密鍵の既知の保管場所が保存元ルートと重なる場合は、除外指定に関係なく停止します。含めるファイルから標準のage秘密鍵を検出した場合も停止します。除外ファイルの本文は読みません。その中に秘密鍵がないことを検出・保証する処理ではありません。

除外したログやキャッシュの変更、出現、消失は取得の照合対象にしません。保存対象の変更、危険な権限、保存元の外へ出るリンク、未対応のファイル種類は取得前または照合時に停止します。

## 取得と保存期限

通常の作業領域はOSの一時領域です。WebとCLIの一時領域が別々の場合は、`WRB_LIVE_WORKSPACE_BASE`に所有者専用の既存ディレクトリ、`WRB_LIVE_PUBLIC_ROOT`に公開領域を指定できます。どちらも正規の絶対パスを使い、作業領域は公開・保存対象と重ならないようにします。変更前の未完了ジョブは移行されないため、完了または取り消してから切り替えてください。

手動取得では「保守あり」と「保守なし」を選びます。保守ありは外部の定期処理や直接DB更新を停止したうえで一時的な保守状態とDBの読み取りロックを使います。保守なしは対応するDB条件で一貫した読み取りを使い、サイトを公開したまま取得しますが、DBとファイルの取得時点には差が残る場合があります。保存対象ファイルの前後照合を行い、検出した不整合があれば完了世代を公開しません。

取得後は保守状態を解除し、サーバー上のPHP CLI（画面と独立して動くPHP処理）で暗号文の転送を継続します。画面を閉じても処理は続き、中断後は「転送を再開」を使います。取得元の本文や生SQLを平文の作業ファイルへコピーせず、小分けにageへ渡します。暗号文と私有の処理記録は上記の作業領域に置きます。一時領域を失った未完了の取得はやり直します。

保存期間の初期値は30日で、1〜3650日を指定できます。期限対象の整理と世代指定の削除に対応し、他の世代が参照する暗号文は残します。サイトのR2キーを持つ主体による削除を防ぐ保証はありません。保存完了と、独立キットによる復旧の確認は別です。

保存容量の節約（世代間共有）は **保存期間と容量** 画面でチェックを入れて有効にします。索引の保存場所は、実行ユーザーのホーム直下の非公開ディレクトリ（`.wordpress-r2-backup-index`、権限`0700`）を自動で選びます。ホームがウェブ公開領域・WordPress本体・OS一時領域に含まれる場合や、所有者専用として検証できない場合は、危険な候補へ切り替えず理由を示して停止します。その場合や保存場所を指定したい場合だけ、詳細設定でサイトとOSの一時領域の外の永続ディレクトリを絶対パスで入力します。配下に保存先・公開鍵ごとの索引を作成します。既存の設定では自動的に有効にしません。保存範囲と除外設定は、この設定と独立しています。

索引を失った場合や共有暗号文が破損した場合は停止します。管理端末の独立キットで索引を再構築するか、共有を明示的に無効にして新しい取得を行います。元サイトと索引がなくても、世代の目録と暗号文から復旧できます。除外付き取得で古いパックに対象外の内容が混在する場合は、今回の対象だけを新しく詰め直します。

新規保存・再利用・除外境界の詰め直しを、内容片の重複を除いた元データのバイト数とパック数で表示します。詰め直しは新規保存の内数です。R2へ転送した暗号文のサイズとは異なり、新しい明細ページと目録は毎世代保存します。

## 対応条件と制限

PHP 7.4以上、intl・mbstring・curl・openssl・dom拡張、WordPressのmysqli接続が必要です。Pythonは不要です。同梱の公式age 1.3.2はLinux amd64とDarwin arm64に対応し、照合値と実行権限を検査します。

同梱のageを起動できず、WordPressから実行権限を設定できない場合は、エラーに記載された `bin/<platform>/age` のSHA-256を確認し、サーバー管理者がPHP実行ユーザーに必要な実行権限を付けてください。

DBは通常のテーブルと生成列に対応します。外部キー（テーブルどうしの参照制約）は、関連する両側のデータをすべて保持する場合、または両側を空にする場合に保持します。一般の部分除外には対応せず、取得前に停止します。VIEW（保存された問い合わせ）、トリガー、ルーチン、イベント、別DBへの依存、検証できない定義やロック権限不足も取得前に停止します。

v4は本文を最大1MiBずつ扱い、最大32MiBまたは512項目のパック（まとめた本文）に保存します。明細ページは最大1MiBまたは1,024記録です。保存元は合計500,000項目、復旧対象の本文は合計1TiBまでです。その他の上限と厳密な条件は[v4形式仕様](docs/v4-format.md)と`src/V4Format.php`にあります。

復旧先は新しい専用ディレクトリです。v4は各保存元を`destination/roots/rNNNN`へ戻し、元の絶対パスへ上書きしません。同じ内容の別ファイルも別の実体へ戻します。DBの照合と内容確認後に元の権限を適用し、対応するリンクは最後に作ります。実サイトのDB取込はSQLを書き出した後の別操作です。

v4は明細をページと分割した記録で処理し、全項目を1つのPHP配列に集めません。所要時間と必要容量・メモリは対象の件数と環境に依存します。旧v3の大規模復旧には別途メモリ指定が必要です。JavaScript依存の動作、外部連携、保存元に実ファイルがない外部参照画像の復旧は、バックアップ完了だけでは確認できません。

PHP標準の`fflush`と、利用できる環境の`fsync`で書き出します。PHP 7.4で停電直前の更新が必ず残る保証はありません。処理中断、保存破損、OSやホストの障害は同じ保証ではありません。

## 定期バックアップ

管理画面で定期バックアップの有効状態と、実行・除外のルールを設定します。基本ルールでは毎時・毎日・毎週を指定できます。毎時は指定時刻の「分」を使います。基本ルールを無効にし、cron式だけで予定を指定することもできます。初期状態では定期実行は無効です。

時刻はWordPressのタイムゾーンを使います。cron式はコマンドを含まない数値ベースの5項目（分・時・日・月・曜日）です。曜日の0と7は日曜日です。除外時間帯は開始を含み、終了を含みません。終了が開始より早い場合は翌日まで除外します。ルールは取っ手または上下ボタンで並び替えられ、上から最初に一致したルールが適用されます。メンテナンス中の開始を避ける場合は、除外を実行ルールより上に置いてください。

予定の保存だけではサーバーの定期実行は登録されません。サーバーのcron（定刻にコマンドを起動する仕組み）から、次のコマンドを毎分呼び出してください。実際のPHPとWordPressの絶対パスへ置き換えます。

```cron
* * * * * /path/to/php /path/to/wordpress/wp-content/plugins/wordpress-r2-backup/schedule.php /path/to/wordpress >/dev/null 2>&1
```

サーバーの起動確認は管理画面へ記録します。実行中・転送待ちのジョブがあれば、その回の定期実行を見送ります。取り逃した予定は連続実行しません。この版で開始した定期バックアップの転送中にR2との接続が途切れた場合や、R2が要求過多（HTTP 429）または一時停止（HTTP 503）を返した場合は、毎分の定期処理が保存済みの位置から同じ転送を自動再開します。暗号文を新規作成する条件付きPUT（同じ名前の保存物を上書きしない転送）に対するHTTP 500も対象です。再開時にすでに存在する暗号文は、全体の長さとSHA-256を照合します。待機は一時エラーの発生から順に1分・5分・15分で、1回のバックアップにつき最大3回です。R2が再開可能な時刻を指定した場合、その定期回を指定時刻より前に再送しません。15分以上待機しても期限が来ていない場合は、次の予定枠で以前の回を未完了として保管します。指定を解釈できない場合も次の予定枠で未完了として保管します。ワーカーが応答を記録する前に停止した場合も、2分以上経過して両方の実行ロックが空いており、取得完了の記録、世代、保存先、設定、転送位置が一致すれば、同じ3回の予算内でその世代を再開します。旧版が HTTP 500 のみ記録して中断した場合は、最終エラーから15分後以降、保存位置にある新規暗号文のサイズとSHA-256が完全に一致する場合だけ、初回の移行再開を行います。

再試行の上限、認証・照合エラー、保存位置を確認できない中断、設定変更では、以前の定期回を新しい予定時刻に「中断」として記録し、新しい世代を開始します。旧世代の工程・件数・実行時の設定は実行履歴に残ります。手動で新規開始した操作、実行中のワーカー、保守状態を優先します。履歴が読み書きできない場合も、操作の識別子と予定を確認して未完了の作業を保管し、次の枠へ進みます。元が定期回で管理者が「転送を再開」を押した場合も、起動直後とワーカー稼働中はその操作を優先し、ワーカーが途絶えたと確認した後に次の枠で未完了保管に移ります。

枠を解放したとき、非公開作業領域の `job-<実行ID>/` に残っている暗号文・チェックポイントを元の位置に保持し、`interrupted-operation.json` に当時の操作を記録します。容量はこのディレクトリ単位で確認できます。この版以降に開始した定期回の保管用作業ファイルは、枠解放から取得時の保存日数を経過した後、定期処理が空いているときに1件ずつ整理します。旧版が作ったファイルとR2上のオブジェクトはこの整理の対象外です。旧版の作業ディレクトリの退避・片付けは、実行ID、履歴、後続世代の照合完了を確認した管理者が行います。

定期実行は現在、保守なし取得に対応する条件だけで開始します。保守ありの定期取得は、外部の書き込み停止を継続して証明する仕組みが未実装のため開始しません。保守中はWordPress管理画面へアクセスできず、その画面で進捗を見られない場合があります。

## バックアップ実行履歴

**R2 Backup → 実行履歴**で、手動・定期の種別、実行時の設定、結果で履歴を確認できます。実行時の設定には保存先、取得方式、保存期間、除外ルールの種類と件数を記録します。現在の除外設定が実行時の記録と一致する場合は、種別ごとに対象名を展開できます。設定が変わっている場合や、行を照合する値など対象名を表示できないルールは、記録済みの件数を表示します。接続キー、個別ルールの値、例外の原文は履歴に保存しません。

R2 Backupの管理画面に開始・完了・失敗の通知を表示し、該当する実行のログに移動できます。転送の再開は元の実行に追記します。完了表示はR2の保存物照合までが対象です。履歴はプラグインの非公開作業領域に保存されます。

## 復旧

独立キットの[CLI・PHP画面の手順](recovery/README.md)を参照してください。復元専用環境で秘密鍵を使い、新しい専用領域と空DBへ復旧します。既存サイトの上書きや公開切替は行いません。

標準MySQL／MariaDBに加え、v4にはSQLiteを使う簡易復旧があります。`restore --sqlite-file`で新しいSQLiteファイルへ取り込み、`--sqlite-site-config`で原本とは別の起動用コピーへURL・DB・専用管理者を設定できます。SQLiteの復旧・起動には`pdo_sqlite`と`sqlite3`拡張が必要です。SQLiteでは未対応の型・定義や値の損失を検出すると停止します。標準DBとの完全な互換性は保証しません。ローカル起動にはmacOSの隔離機能を使う`--serve-local yes`経路があります。

管理画面の復元操作には管理権限、nonce（操作の偽造を防ぐ確認値）、パスワードの再入力が必要です。専用領域は実行ユーザーのホームの`.wordpress-r2-backup-restore`（`WRB_RESTORE_STATE_DIR`で変更可）、MySQLの接続セットは`WRB_RESTORE_MYSQL_CONNECTIONS`で指定します。

## 開発時の検証

開発用依存物は`composer install --no-scripts --no-plugins --prefer-dist`で構築します。PHPUnitの設定は`phpunit.xml`です。DB・Web・R2の統合試験には、試験専用の環境と対応する実行ファイルが必要です。実サイトの接続設定や実データを試験環境へコピーしないでください。

管理画面の同時操作の試験は、PHP-FPM（複数のPHP処理を同時に動かす方式）とNginxを使います。`WRB_TEST_FPM_BIN`と`WRB_TEST_NGINX_BIN`へ実行ファイルの絶対パスを設定し、FPMのPHP版を試験実行PHPと合わせます。通常のプラグイン起動には不要です。
