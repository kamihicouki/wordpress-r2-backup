# WordPressを独立キットで復旧する

この手順は、元サイト、取得ジョブ、送信元索引を使わず、保存先と管理者の秘密鍵からファイルとDB（データベース）を復旧するためのものです。キットの`recover.php`はCLI（コマンドで操作するプログラム）です。秘密鍵は標準入力から渡し、WordPressへ送信しません。

[GitHub Releases](https://github.com/kamihicouki/wordpress-r2-backup/releases)の独立復旧キットZIPはMacのAppleシリコン向けです。Linux amd64ではプラグインZIPを専用環境へ展開し、`recovery/recover.php`を使います。以下の実行例では`--age`の引数を、そのZIPに含まれる`bin/linux-amd64/age`の絶対パスに置き換えてください。

新規キットは目録v1・v2・v3・v4を読みます。v1・v2は従来の合成環境向け、v3は旧WordPress取得、v4は0.4.0以降のWordPress取得です。管理画面の設定と取得条件は、配布元プラグインのREADME.mdを参照してください。

v4の復旧先は、新規の`destination/roots/rNNNN`です。保存元が複数あれば、ルートごとに分かれます。目録に記録した元の絶対パスへは上書きしません。元の権限を復元し、同じ内容の別パスも別のファイル実体へ戻します。対応するリンクは通常ファイルの後に作ります。

v4は本文を分割したパックと明細ページを使います。世代間の内容共有に対応し、選択した1世代だけで復旧対象を決められます。`rebuild-index`は、暗号化した世代の目録・明細ページ・全パックを復号照合し、秘密鍵を含まない永続索引を新しく作ります。形式と上限は、キット内の`docs/v4-format.md`を参照してください。ソースリポジトリにも同名の仕様書を同梱しています。

v4はSQL（DB復旧用の記述）を組み立て、指定された隔離DBへの取込後に件数・値・定義・外部キー（テーブルどうしの参照制約）を照合します。元のSQLモード、時刻・文字コードの条件、バイナリ値、生成列の定義を保持します。定義の照合ではMySQLが冗長に表示する文字コード指定だけを正規化し、保存する定義本文は書き換えません。VIEW、トリガー、ルーチン、イベント、別DBへの依存はv4取得前に停止します。

v4の約23万ファイル相当の目録生成・`inspect`は、PHPのメモリ上限128MiBで確認済みです。復元後は、照合済み原本を保管し、別コピーで必要なページ、保存済み画像、管理画面を確認してください。JavaScriptや外部サービスに依存する動作も別途確認してください。外部URLを参照する画像は、保存元に実ファイルがなければ復旧されません。

旧v3のアーカイブ復旧は件数に応じたメモリを必要とし、約23万項目では`php -d memory_limit=1G recover.php ...`を指定します。v3で所有記録の確定前に中断した場合は、自動再開せず停止します。`discard`で作業領域を破棄し、別の新規復旧先へやり直します。

## 実R2からの独立復旧

画面から取得した復旧用接続ファイルはR2キーを含みます。手元で0600へ保護し、秘密鍵とともにサイト外へ保管します。バックアップ設定で登録するのは公開鍵です。秘密鍵は復元を実行する環境の復元画面または復旧コマンドで使用します。

```sh
chmod 600 wrb-r2-connection.json
php recover.php list --direct-r2-connection-file wrb-r2-connection.json --unit <接続ファイル内のunitId> --age ./dependencies/age/age
php recover.php inspect --direct-r2-connection-file wrb-r2-connection.json --unit <unitId> --age ./dependencies/age/age --snapshot <世代ID> < administrator.key
```

v4の`restore`は新しい領域へファイルを復旧し、隔離DBの接続引数を指定すると、新しい空DBへの取込と厳密照合も行います。SQLをファイルへ取り出す場合は、次の`export-database`を使います。出力先ディレクトリは0700にし、既存ファイルは上書きしません。既存サイトや既存DBへの上書きは行いません。

```sh
mkdir -m 700 recovery
php recover.php export-database --direct-r2-connection-file wrb-r2-connection.json --unit <unitId> --age ./dependencies/age/age --snapshot <世代ID> --sql-output /absolute/path/recovery/database.sql < administrator.key
```

以降にはキット作成と保存先別の操作例を示します。`--direct-r2-connection-file`は実R2、`--r2-connection-file`と`--synthetic-connection-file`はローカル検証用です。各コマンドでは保存先の選択引数を1つだけ使います。

## C3管理画面で公開鍵の復号能力を確認する

隔離したWordPressの「ツール → 合成バックアップ」で、異なるage公開鍵を2名分登録します。秘密鍵はWordPressへ送信しません。「2名分の確認ファイルを作り直す」で両方の公開鍵向けに確認用暗号文を発行し、各欄の「確認用暗号文を取得する」で取得します。各ファイルはその欄の公開鍵1本だけに暗号化されています。取得時の固定ファイル名は`wrb-key-challenge.age`です。取得後は手元で区別して保管してください。

対応する秘密鍵を保管する手元の端末で、キットに同梱したageを実行します。次の`private-key`はキット外の所有者専用鍵ファイルです。

```sh
/path/to/recovery-kit/dependencies/age/age --decrypt --identity /dev/stdin wrb-key-challenge.age < private-key
```

復号したJSON（項目名と値を持つ形式）の`slot`と画面の欄が一致することを確認し、`code`だけを同じ欄へ入力します。平文とcodeをログ・画面共有・他のサービスへ貼り付けないでください。codeは15分以内に確認し、失敗上限は5回です。確認済みの暗号文は再利用できません。再登録または再発行すると両名の確認が解除されます。各公開鍵の復号能力を確認する手順であり、物理的に別々の人が操作したことを証明するものではありません。

管理画面の世代一覧では保存物だけを検証し、目録本文は未検証です。作成した合成世代は、元サイト外で以下の`list`と`inspect`を使い、両方の秘密鍵で確認してください。キットと秘密鍵は分離して保管します。管理画面からキットは作成しません。

## キットを元サイト外へ作る

公式配布物`age-v1.3.2-darwin-arm64.tar.gz`を[age 1.3.2の公式リリース](https://github.com/FiloSottile/age/releases/tag/v1.3.2)から取得します。生成処理は固定したSHA-256と一致した配布物だけを展開します。出力先はGit管理領域外の新規ディレクトリを指定します。

```sh
php recovery/build-kit.php \
	--output /private/tmp/new-recovery-kit \
	--age-archive /private/tmp/age-v1.3.2-darwin-arm64.tar.gz
```

生成処理はComposerの`install --no-dev --no-scripts --no-plugins`で本番用の読み込み設定を作ります。Composerの既定位置は`/opt/homebrew/bin/composer`です。別の位置なら`--composer /absolute/path/to/composer`を指定します。

出力先の権限は所有者専用の`0700`です。`recover.php`・`recover-web.php`・`local-router.php`、`library/`内の実装・依存物・画面資産・復元ワーカー・ライセンス、`dependencies/age/age`と公式ライセンス、`docs/format-and-design.md`・`docs/v4-format.md`、このREADMEを含みます。`dependencies/versions.json`は取得元・配布物の照合値・必要環境を記録します。`readableManifestVersions: [1, 2, 3, 4]`は、新規キットが読める目録の版です。既存キットは変更しません。v4には、この対応版を記録した新しいキットを使います。`SHA256SUMS.json`は各同梱ファイルのSHA-256を記録します。この一覧自体のハッシュは、保管先と別の信頼できる場所に記録してください。

`dependencies/versions.json`の`sqliteRecovery.extensions`は、SQLiteへの取込と任意の起動用コピー作成に必要なPHP拡張の一覧です。取込には`pdo`・`pdo_sqlite`、起動用コピーのDB複製には追加で`sqlite3`が必要です。これらは実行先で用意する拡張であり、キットへの同梱や、生成時の動作確認済みを意味しません。保存されたバックアップの目録とは別の、キットの必要環境の記録です。

キットには秘密鍵、送信元索引、接続ファイル、保存先データ、模擬サーバー、PHPUnitを含めません。キットと各管理者の秘密鍵は別々に保管します。鍵はそれぞれの管理者が保護した端末で扱います。

送信元索引・取得ジョブ・接続サービスの管理台帳は、復旧には不要です。模擬HTTP経由ではreader（読み取り用）の接続ファイルを指定します。writer（取得用）やadmin（管理用）のファイルは流用しません。実R2の復旧用接続ファイルはサイトのR2キーを含むため、読み取り専用の権限を保証するファイルではありません。元サイトの接続ファイルを失った場合の実Cloudflare再認証は後続工程であり、このキットではまだ提供していません。

## ローカルR2から直接読む

`--r2-connection-file`は公式Miniflare 4.20260722.1のS3経路を直接使います。接続サービスと管理台帳は必要ありません。接続先は`http://127.0.0.1:port`だけです。実Cloudflareの接続先へ切り替える機能はありません。

```sh
php recover.php list \
	--r2-connection-file /private/r2-reader.json \
	--unit 64桁の管理単位ID \
	--age /private/recovery-kit/dependencies/age/age
```

接続ファイルは`format`が`wrb-local-r2-reader-v1`、`version`が`1`で、`unitId`、`endpoint`、`bucket`、`accessKeyId`、`secretAccessKey`、`expiresAt`の計8欄です。絶対パス・所有者専用の`0600`を要求します。資格情報をコマンド引数、URL、環境変数へ記載しません。SDKのS3経路は内部で固定し、別の任意パスへ秘密値を送りません。

暗号文1個の上限は128MiB、各片は16MiBです。各片と全体の長さ・SHA-256を受信後に照合し、途中失敗時は復旧先へ公開しません。旧形式の単体暗号文も読み、旧実体と構成記録が同じ論理キーに併存したら拒否します。

ローカルSDKのS3資格情報では、本番のIAM（保存先側の権限制御）による読み取り専用権限は検証できません。このreaderが発行する操作は読取だけです。本番の読み取り専用資格、Cloudflare再認証、失効は、このローカル経路では検証しません。

## 完了世代を選ぶ

キットのディレクトリで実行します。保存先、管理単位、ageの場所は毎回明示します。環境変数や元WordPressから推測しません。

```sh
php recover.php list \
	--repository /private/backup-store \
	--unit 64桁の管理単位ID \
	--age /private/recovery-kit/dependencies/age/age
```

模擬HTTP保存先では、`--repository`の代わりに所有者専用の接続ファイルを指定します。両方の指定、または両方の省略は拒否します。`--unit`と`--age`は引き続き必要です。

```sh
php recover.php list \
	--synthetic-connection-file /private/synthetic-connection/reader.json \
	--unit 64桁の管理単位ID \
	--age /private/recovery-kit/dependencies/age/age
```

接続ファイルはキット外の`0600`ファイルとし、親領域も所有者専用にします。模擬サーバーが発行した期限内の読み取り用ファイルを使います。ファイルの中身やトークンを引数、URL、ログへ貼り付けないでください。CLIは接続先を推測せず、`http://127.0.0.1:<port>`だけを許可します。明示した管理単位と接続ファイルの管理単位が異なる場合は通信前に停止します。これは実R2の認証・削除保護の検証ではありません。

模擬HTTP経路では1個の暗号文を64MiB以下に制限します。超過は転送前に拒否します。この試験上限はローカル保存経路に適用しません。分割転送、複数送信元の排他、古い索引の無効化は後続工程です。

`list`は追記された完了記録の`snapshotId`をJSONで返します。この一覧では目録を復号しません。実R2への直接接続では、全完了世代が参照する暗号文を読み戻して長さとSHA-256を照合するため、保存量に応じた通信が発生します。軽い疎通確認には使わないでください。本文の復号と復元内容の照合は、選択世代の復旧時に行います。未完了の世代は一覧へ出しません。完了記録や保存物が破損している世代には`valid: false`と安全な理由を表示します。他の正常な世代は選択できます。

## 復旧前に取得証拠を確認する

`inspect`は秘密鍵を標準入力から受け取り、目録を復号して検査します。復旧先とDB接続は不要です。元サイト、送信元索引、取得時の`capture.json`も使いません。

```sh
php recover.php inspect \
	--repository /private/backup-store \
	--unit 64桁の管理単位ID \
	--age /private/recovery-kit/dependencies/age/age \
	--snapshot 64桁の世代ID \
	< /private/administrator-key/identity.txt
```

成功時は要約JSONだけを標準出力へ返します。`verification.manifest`と`referencedCiphertexts`は目録と参照暗号文の検査結果です。ファイルとSQLの本文は復号しないため、`payloadDecrypted`と`databaseImported`は`false`です。本文の内容検査とDB取り込みを完了した意味ではありません。v4は明細ページも復号して参照を照合し、`pagesDecrypted: true`を返します。パック内のファイル本文やSQLは`inspect`では復号しません。

目録v2は`captureEvidence: reported`と`capture`に取得方法、開始・固定・解除・記録確定時刻、ファイル件数、保存方式の集合、DB在庫件数、定義件数、取得元DB版を返します。`tableCount`はテーブルとビューを含むDB在庫件数です。v2の取得要約には、元パス、テーブル名、生の固定記録、秘密鍵、SQL本文を表示しません。時刻はUTCです。目録v1は`captureEvidence: unknown`と`capture: null`を返します。`capturedAt`は取得証拠が示すDB固定時点の代わりにはなりません。v4の取得要約には、保存範囲の照合値、ルート数、内容の集計と取得時刻を返します。保守ありの場合はロック取得・照合時刻を、保守なしの場合はDBの読み取り開始・DB照合・ファイル照合の時刻をそれぞれ示します。保守なしではDBとファイルが同じ時点の状態とは限りません。

取得元DB版の表示は、その版で作られた記録の観測値です。他のDB系列や版との互換性を保証しません。実証範囲は合成取得と隔離したMySQL 8.0.35です。任意の実サイト、書き手停止、運用目標の達成は未実証です。

旧v1・v2・v3の`restore`と`resume`は、本文復号・DB取り込み・復旧先公開より前に取得要約を返します。v4は本文を復号して照合した後、DB取り込みと復旧先公開の前に返します。出力はいずれも標準エラーへの1行のJSONです。従来の最終結果JSONは標準出力へ返します。再開時の要約も、その回の目録と参照暗号文の検査結果を表します。

## 選択した世代を新規領域へ復旧する

秘密鍵は標準入力へ渡します。引数、環境変数、ログへ秘密鍵の値を入れません。次の例の鍵ファイルはキット外の所有者専用領域に置きます。

```sh
php recover.php restore \
	--repository /private/backup-store \
	--unit 64桁の管理単位ID \
	--age /private/recovery-kit/dependencies/age/age \
	--snapshot 64桁の世代ID \
	--destination /private/restored-new-site \
	< /private/administrator-key/identity.txt
```

`restore`、`resume`、`discard`、`rebuild-index`も同じ保存先の選択引数を使います。模擬HTTPでは前節の`--synthetic-connection-file`へ置き換えます。

`restore`の復旧先は未作成の新規領域に限ります。既存の空ディレクトリも上書きしません。復号後のハッシュ、サイズ、全パスを検証してから公開します。選択した世代の全構成を使い、その世代で削除されたパスを復活させません。鍵の標準入力は最大64KiBで、秘密鍵を一時ディスクへ退避しません。

DB引数を省略すると、標準エラーに「DB未取込」を表示し、結果JSONの`databaseImported`は`false`です。SQLは復旧先へ自動公開しません。v4で保存された`wp-config.php`などの秘密設定ファイルは、他の保存ファイルと同様に専用復旧先へ戻ります。

DBも取り込む場合は、次の5引数をすべて追加します。専用ソケットで起動した所有者専用の隔離MySQL作業領域と、`wrb_test_`で始まる名前の新規空DBだけを受け付けます。既存のLocal環境のDBは使いません。

```sh
	--mysql /absolute/path/to/mysql \
	--mysqldump /absolute/path/to/mysqldump \
	--defaults-file /private/synthetic-mysql/client.cnf \
	--mysql-workspace /private/synthetic-mysql \
	--database wrb_test_new_target
```

接続設定は専用作業領域内の`0600`ファイルに置きます。DB名だけや接続設定だけの指定は拒否します。取り込みで失敗したDBへ同じSQLを無条件に再実行しません。形式による再開条件は後述します。既存DBの削除や作り直しはCLIが行いません。

### MySQL本文は取込専用アカウントで実行する

`--defaults-file`は、空DB・イベント・復元結果を確認するための接続設定です。復元SQLの本文をこの接続で実行しません。本文用には別の新規アカウントを準備し、`--mysql-workspace`の直下へ`importer-<DB名>.cnf`を0600で置きます。ファイル形式は`[client]`の`user`・`password`・`socket`だけです。専用アカウント名は確認用接続と異なる名前にし、同じ専用サーバーの私有ソケットを指定します。設定が無い場合に管理接続へ戻る動作はありません。

準備する管理者は、次を確認してください。キット自身が管理アカウントやDBサーバーを作成する機能はありません。

1. 信頼する使い捨てサーバーに、新しい空DBとランダムな名前の専用アカウントを作る。匿名アカウント・匿名の権限指定がなく、同名アカウントの別接続元による権限がないことを管理側で確認する。
2. v4では対象DBだけの`CREATE, INSERT, SELECT, REFERENCES`が最小の候補。旧形式では必要なDB内の権限を追加する。グローバル実権限、ロール、代理権限、権限を再付与する権利を与えない。
3. DB名の`_`は権限指定でワイルドカードになり得る。MariaDBとMySQLの`partial_revokes=OFF`では各`_`を`\_`へエスケープする。MySQLの`partial_revokes=ON`ではDB名をそのまま完全一致で指定する。バッククォートで囲むだけでは前者のワイルドカードを無効にできない。
4. 取込中に別の管理者が権限・ロール・サーバー設定を変更しない。既存の危険な拡張や共有業務データを持つサーバーを復元試験に使わない。

取込側でも実効ユーザー・ロール・権限の表示・DB名の解釈を検査し、対象DB外の権限や未知の表示を拒否してからSQLを読みます。ただし権限表示だけで任意の既存サーバーの全権限を証明できるわけではないため、上記の準備側の確認も必要です。保存物の照合値一致はSQLの命令が安全という証明ではありません。

旧形式で別人の`DEFINER`（定義の実行権限を持つ所有者）を保持するために管理権限が必要な場合は、昇格やSQLの無断書換えをせず失敗します。失敗したDBへの再取込は禁止のままです。これはDB権限による本文の制限であり、OSの隔離やCPU・容量の制限を提供するものではありません。

## 隔離DBのイベントを実行させずに取り込む

新しいキットのDB取込は、専用の合成MySQLを起動時に`--event-scheduler=DISABLED`で設定した場合だけ許可します。`OFF`は別の接続から途中で有効化できるため、取込条件を満たしません。キットがサーバー全体の設定を変更することはありません。

0.5.7では、イベント定義のないv4のDBをMariaDB 10.5.29へ取り込めます。MariaDBは`DISABLED`時に`information_schema.EVENTS`を照会できないため、既存イベントを`mysql.event`で確認します。MariaDBのイベント定義の取込は未対応で、定義がある世代は取込前に停止します。自動実行を有効化して回避しません。旧形式のMySQL 8経路は維持します。

元SQLを変更せずに同じ取込接続のイベント作成数を確認し、取込後に残った定義数と照合します。取得証拠がある目録v2ではイベント名も照合します。MySQLが警告だけで期限切れの定義を作らなかった場合も、正常終了にはしません。失敗したDBへ無条件に再取込せず、別の新規空DBを指定します。

旧形式の取込対象はMySQL 8のmysqldump出力と、区切りに`;`を使う通常の合成SQLです。最後の文は`;`なしでも取り込めます。`DELIMITER`で区切りを変更するSQLは、mysqldump出力と同じく最後に`DELIMITER ;`へ戻す必要があります。意図的にイベントを作ってから削除するSQL、作成を重複させるSQL、接続の集計値を初期化する任意のSQLプログラムを実行する機能ではありません。旧合成形式ではイベント定義を保持します。v4のWordPress取得は、イベントを検出すると取得前に停止します。

## 中断した復旧を再開または破棄する

`restore`を`resume`に置き換え、同じ保存先・単位・世代・復旧先と秘密鍵を指定します。再開処理は進行記録と復旧先を再照合し、変更を検出したら停止します。DBの扱いは形式ごとに異なります。

- v4は、同じ保存先・単位・世代・復旧先・DB名で再開します。取込成功を記録済みなら同じDBを再利用して値・定義・参照関係を照合し、二重に取り込みません。取込を試みたまま中断した場合は再開できません。新しい空DBと新しい復旧先を用意し、`restore`からやり直します。
- 旧v1・v2・v3は、DB失敗後に別の新規空DBを用意し、`resume`へ新しいDB引数をすべて指定します。DB取込後に公開が中断した場合も、再開には別の新規空DBが必要です。

公開途中で中断した場合、`resume`はジョブの所有記録と復旧先の実体を照合し、公開済みのパスも検査してから残りを公開します。旧形式は検証済みの作業用ファイルを維持します。v4はページとパックを再検査し、所有を照合できた復旧先へファイルを組み立て直します。他の処理が作った復旧先、内容が一致しないファイル、未知のパス、所有証明が一致しない部分公開先は再利用しません。旧形式では使用済みのDBへの二重取り込みを拒否します。v4の記録済み成功DBの再利用は、前述の照合を行う場合に限ります。

復旧先のディレクトリを新規作成してから所有記録を保存するまでの間に強制終了した場合は、所有を証明できないため既存先として拒否します。この場合は別の未作成の復旧先を指定して`restore`してください。部分公開された領域が存在するだけで復旧成功とは判断しないでください。

全内容の公開と最終検証後、所有マーカーを削除してから作業領域を片付けるまでの間に強制終了した場合も、再開は安全停止します。この時点の公開先は完成済みですが、完了報告を受け取っていない場合は成功扱いにせず、別の新規先への復旧と照合で確認してください。所有を確認できない既存先は自動で変更・削除しません。

旧形式のファイル復号途中の中断では、確認済み単位を保って同じジョブを再開します。再開時に未知・改変内容を検出した場合は、作業領域を自動削除せず停止します。新キットは従来の進行記録も読みますが、新キットで開始した作業を旧キットへ戻して再開することはサポートしません。旧キットが復号途中に残した未記録ファイルは、自動採用や自動削除の対象にしません。

そのジョブの一時領域を破棄する場合は、`discard`と同じ保存先の選択引数、`--unit`、`--age`、`--snapshot`、`--destination`を指定します。秘密鍵は不要です。指定ジョブが所有する一時領域だけを後始末し、公開済み復旧先やバックアップ保存物は削除しません。

処理の失敗は非ゼロの終了コードで返します。表示する理由は処理段階に限定し、子プロセスの診断や秘密を含み得る例外本文を表示しません。

## 消失した共有索引を再構築する

`rebuild-index`は旧合成形式とv4に対応します。v4では接続先アカウント・バケット・管理単位・現在の公開鍵集合が一致する保存範囲を検証し、その範囲の索引を再構築します。

旧合成形式では、同じ管理単位と公開鍵集合で同じファイル内容を複数の名前や世代から共有します。DBと目録は各世代で保存します。公開鍵集合を変更した後は旧集合の暗号文を共有しません。

送信元の索引がなく保存先に既存実体がある場合、新規取得は停止します。復旧は索引を必要としません。管理者端末で次の操作を行い、現在の公開鍵集合を明示して新規索引を作ります。

```sh
php recover.php rebuild-index \
	--repository /private/backup-store \
	--unit 64桁の管理単位ID \
	--age /private/recovery-kit/dependencies/age/age \
	--recipient age1管理者Aの公開鍵 \
	--recipient age1管理者Bの公開鍵 \
	--index-directory /private/new-index \
	< /private/administrator-key/identity.txt
```

再構築は保持中世代の参照先と現在の鍵集合の共有実体を検証します。実R2では接続先アカウントとバケットを正本にし、別アカウントの目録を転用しません。v4では未参照パックも同じ保存範囲に限って全内容を照合し、出自不明として登録します。その再利用には、全内容が次の取得対象に含まれることを要求します。秘密鍵を索引に含めません。

`--index-directory`には新しい空の私有領域を指定します。完了したv4索引を送信元の専用領域の`<scopeId>`ディレクトリへ置きます。稼働中の索引を上書きせず、未完了のバックアップを取り消してから切り替えます。送信元へ渡すのは検証済み索引だけです。再構築した索引は新しい識別子を持つため、古い索引に結び付いた転送途中のジョブはそのまま再開しません。

保存APIは既存キーの上書きと削除を拒否します。OS管理者による削除防止や実R2のロックを証明するものではありません。古い共有実体を新世代が参照するため、作成日だけによる一律期限削除は使いません。実R2の通常取得は保存期間と世代指定の削除に対応し、共有参照を確認して暗号文を整理します。サイトのR2キーを持つ主体による削除を防ぐ保証はありません。OAuthと、接続ファイル消失後のCloudflare再認証は未実装です。v4の世代間共有は、設定画面の「保存期間と容量」で「保存容量を節約する」を選んで有効にします。索引の保存先は通常、サーバー実行ユーザーのホーム直下の非公開領域が自動で選ばれ、安全に選べない場合に限り詳細設定で手動指定します。

## CLIの一時索引キャッシュを調整する

復元時の一時索引がSQLiteの場合、信頼できるCLI実行環境の`WRB_RECOVERY_METADATA_CACHE_MIB`で接続ごとのキャッシュ容量を指定できます。未指定は従来どおり2MiBです。指定値は先頭ゼロ・符号・空白のない十進整数の2〜1024に限定し、不正な値は索引作成前に拒否します。例として`WRB_RECOVERY_METADATA_CACHE_MIB=64 php recover.php restore ...`のように指定します。HTTP経由の入力やWeb復元画面では設定できず、CLI以外ではこの環境変数を参照しません。

作成時の設定を保持し、照合用に開き直す読み取り専用接続にも同じ容量を適用して読み戻します。これは一時索引のSQLiteキャッシュだけの設定で、WordPress用SQLite DBの設定やバックアップ形式は変更しません。総メモリの上限ではないため、PHP・OSのファイルキャッシュ・その他の処理を含めた実行環境の余裕を確認してください。実行中の索引へ別接続で設定を変更せず、次の新規試行から適用します。内容の認証・ファイル同一性・全件照合・同期の検査は維持します。

## 標準DBと簡易SQLiteを選ぶ

標準復元は従来どおりMySQL／MariaDBの新しい空DBを使います。大きなDBで操作の既定期限300秒を超える場合だけ、`--mysql-timeout 3600`のように秒数を明示します。1〜86400秒に限定し、接続期限と取得元の読み取りロック期限は延長しません。失敗したDBへ再取込せず、新しい空DBを指定します。

簡易復元はMySQLサーバーを使わず、PHPとSQLiteでWordPressをローカル起動する方式です。一時索引のSQLite化とは別機能です。v4だけに対応し、旧形式や既存SQLiteファイルへの取込・SQLiteのresumeは拒否します。所有者専用0700の親ディレクトリと、まだ存在しないSQLiteファイルのパスを指定します。ファイルは製品が0600で新規作成します。取込にはPHPの`pdo`・`pdo_sqlite`と同梱のWordPress公式SQLite互換層、後述の起動用コピー作成には追加で`sqlite3`が必要です。暗号文の復号には従来どおりageが必要です。 SQLiteではAPIからの再開も拒否し、中断時は新しい空DBと復元先でやり直します。再開に使わない内部台帳は一時扱いにしますが、復元ファイル自体の同期と全件照合は維持します。

大きな表の全値照合では、SQLiteの並べ替え用一時領域にも十分な空き容量が必要です。小容量の一時メモリー領域では、値が正しくてもSQLiteコード13（作業容量不足）で停止する場合があります。必要な場合は、PHPの起動前に`SQLITE_TMPDIR`でWeb公開領域外の所有者専用0700ディスク領域を指定し、鍵を扱う一時領域とは分離します。ここには復号済みの行データが一時保存され得るため、公開・共有せず、終了後の残留も確認してください。age秘密鍵用の一時領域を変える必要はありません。照合失敗を成功へ読み替えたり、失敗したSQLiteファイルへ再取込したりしません。

復元画面から開始したSQLiteジョブでは、復元作業領域の各ジョブ内に所有者専用の一時フォルダーを自動作成し、復元を担当するPHPの起動前に指定します。コンテナでは、復元作業領域に十分なディスク容量を割り当ててください。

```sh
php recover.php restore \
  --repository /private/verified-ciphertexts \
  --unit 管理単位ID --snapshot 世代ID \
  --age /private/recovery-kit/dependencies/age/age \
  --destination /private/new-restored-original \
  --sqlite-file /private/new-database/original.sqlite \
  < /private/administrator.agekey
```

MySQL用の5引数とは併用しません。元のバックアップをSQLite形式へ書き換えず、復元先だけで変換します。元定義、変換後の物理定義・列・主キー・一意制約・外部キー、件数と全値の照合を通過してからファイルを公開します。互換層で小数の桁や巨大な整数などの値を保持できない場合は成功扱いせず停止します。CHECK・FULLTEXT・SPATIAL・一意索引の接頭辞など、今回保証しない定義も停止します。あらゆるMySQL機能・テーマ・プラグインの互換性を保証する方式ではありません。

### 別コピーを作ってローカル起動する

上記に`--sqlite-site-config /private/local-site.json --serve-local yes`を加えると、照合済み原本を保持し、別のサイトとDBへURL変更・SQLite接続・専用管理者を設定して起動します。設定ファイルは所有者0600、16KiB以内のJSONです。次の7欄をすべて指定します。

設定値と出力先だけで分かる不備は、復号・DB取込の前に検査します。表の接頭辞、URL、別名URL、管理者指定、未使用の出力先、親領域の保護と保守中の印を確認します。起動用サイトとDBは、復元原本の保存先・元SQLiteファイル・同梱実装と重ならない別の領域へ置いてください。起動時にも実ファイルと隔離条件を再検査します。データの中身に依存する非互換は、事前検査だけで検出できるとは限りません。

```json
{
  "root": "r0001",
  "siteDirectory": "/private/new-running-site",
  "databaseFile": "/private/new-running-db/site.sqlite",
  "sourceUrl": "https://source.example",
  "localUrl": "http://127.0.0.1:18821",
  "tablePrefix": "wp_",
  "administrator": {"login": "restore-check", "passwordHash": "WordPress portable password hash"}
}
```

例のハッシュをそのまま使うことはできません。専用のランダムなパスワードから、復元したWordPressの`PasswordHash`で作った`$P$`形式のハッシュを使います。パスワードやハッシュを引数・URL・共有ログへ記載しません。管理者を作らない場合は`administrator`を空配列にします。除外した元の管理者情報を復活させる機能ではありません。

`siteDirectory`とDBは新規パスだけを使い、DBを公開領域へ置きません。元のプラグイン有効状態は維持しますが、起動用コピーでは`wp-config.php`、DB差し替え、キャッシュ差し替えを再設定します。シリアライズ済み文字列と配列の長さを再計算し、オブジェクトなど安全に変換できない値は停止します。

`--serve-local yes`は現在macOS専用です。OSの隔離機能で外向きTCPとUNIXソケット接続を拒否し、MySQLにも接続できません。PHPは既存のini設定を読み込まず、外部コマンド実行・メールなどを停止し、127.0.0.1の指定ポートで待ち受けます。静的ファイルにもブラウザー向け通信制限を付けます。停止はCtrl-Cです。サーバーの私有ログはサイト親の`.wrb-serve-*`に保存します。別途ブラウザー側の第三者通信遮断も行って検証してください。LinuxやWindowsでこの隔離条件を弱めて起動する迂回は提供しません。

元サイトと公開済み復元先を置き換えるWeb復元画面は、このコマンドとは別の未実装機能です。

### ローカル試験でメディアを配置しない

WordPressシステムとDBの起動確認に絞る場合は、`restore`へ`--sqlite-site-config /private/local-site.json --local-media-dry-run yes`を加えます。メディアだけをdry run（内容を検証し、復元先へ配置しない操作）にし、WordPress本体・テーマ・プラグイン・DBは実際に復元します。テーマやプラグイン内の画像・CSS等は配置対象です。

選択した保存元ルートの標準`wp-content/uploads`だけが非配置対象です。設定ファイルの`localUrl`は`http://127.0.0.1:18826`のような、明示した1024〜65535番のローカルポートに限定します。標準uploadsがない場合は停止し、カスタムの保存場所や追加ルートを勝手にメディアと推定しません。追加ルートは通常どおり配置するため、別の場所にメディアを保存する構成ではこの指定だけで全メディアを省略したと扱わないでください。ローカルサーバーの起動まで行う場合は、前節の`--serve-local yes`も指定します。

全保存物・全メディアの内容と、DBの定義・全値の照合は維持します。省略するメディアを参照・通過するシステムのリンクは停止対象です。結果の`files`・`directories`・`links`・`bytes`は実配置分、`mediaDryRun`は内容を検証して配置しなかった分です。`restoreMode`は`local-system-media-dry-run`になります。この試験ではアップロード画像の実表示を完了条件にしません。

起動コピーを準備する従来の指定はv4と新規SQLiteのローカル試験に対応します。既存の復元先や失敗したDBへ上書きせず、新しい所有者専用領域で実行してください。取得済みの世代や除外設定を変更する操作ではありません。

### システムの展開とDB取込だけを先に完了する

MySQL／MariaDBでもSQLiteでも、起動コピーの作成が不要なら、`--sqlite-site-config`の代わりに`--local-system-root r0001 --local-media-dry-run yes`を指定できます。保存済みのルート名を明示し、未作成の復元先と新しい空DBだけに復元します。標準uploads以外のメディア保存場所や追加ルートを推定して省略しません。

```sh
php recover.php restore \
  --repository /private/verified-ciphertexts --unit 管理単位ID --snapshot 世代ID \
  --age /private/recovery-kit/dependencies/age/age \
  --destination /private/new-system-original \
  --sqlite-file /private/new-database/original.sqlite \
  --local-system-root r0001 --local-media-dry-run yes \
  < /private/administrator.agekey
```

標準DBでは`--sqlite-file`をMySQLの5引数へ置き換えます。対象DB専用の限定アカウントも前述のとおり準備します。SQLite起動設定との併用、DB未指定、不完全なMySQL引数、不正なルート名は開始前に拒否します。この入口はURL変更・接続設定の作成・管理者の追加・Webサーバー起動を行わず、結果に`site`は付きません。後から起動する際は、別コピーでこれらの設定と通信隔離を行ってください。

MySQLで公開途中の復元を再開する場合は、`resume`にも同じ`--local-system-root`と`--local-media-dry-run yes`、元の接続を指定します。全量復元からの切替や別のルートへの切替は拒否します。DB取込を試みたまま失敗した場合は、新しい空DBと復元先でやり直します。SQLiteの中断再開は提供しません。

所要時間はダウンロード完了後から、復号・全保存物の検証・DB取込と全値照合・システム配置・配置後と権限の照合までを測ります。ファイルとDBの規模、機器や実行環境に依存します。時間短縮のために照合を省略したり、DBの耐久性を緩めたりしません。

開発用バックアップに同じサイトの本番URLなどが残る場合は、設定JSONへ任意の`sourceAliases`配列を追加できます（最大8件）。元URLとこれらの別名URLを同じローカルURLへ写します。外部画像を取得する機能ではありません。別の事業者のURLを指定しないでください。

URLの置換は、長い別名から評価し、元URLが別ホスト名・ポート・利用者情報の一部に一致する場合は置換しません。通常表記、JSONでスラッシュをエスケープした表記、シリアライズした文字列・配列に対応します。ホスト名の大小文字違い、絶対ファイルパス、カスタムのメディア保存場所の移行は行いません。

v4の標準MySQL出力は1行ずつのINSERTであるため、取込セッションでは行ごとの自動確定を止め、末尾に明示的なCOMMITを置きます。DDL（表定義の変更）が暗黙に確定する場合があるので、失敗時にDB全体が元へ戻る保証ではありません。失敗先への再取込拒否を維持します。

通常のv4復元は、検証済みtar内の位置から内容を読み、個別の一時ファイルへの展開を省きます。読み取りごとのファイル同一性・サイズ・照合値の確認は維持します。ジョブ内部の`state.json`には、事前検証・DB取込・DB照合・ファイル配置・ファイル照合・権限照合・片付けの段階を記録します。SQLiteの件数と表ごとの照合進捗は標準エラーへ表示し、最終結果JSONと区別します。

## 統合復元画面

WordPressプラグインの復元タブと、この独立キットの`recover-web.php`は同じ1画面と同じ復元処理を使います。保存元→復元先→DBの方式と接続→変更後のURL→事前検査→確認→実行・進捗・起動の順に見渡せます。

対応範囲は新しい専用領域と新規の空DBです。任意のホスト、既存DB、既存サイトへの上書き、公開運用への切替は行いません。v4の世代だけに対応します。DNSも変更しません。

「URLの設定方法」は初期状態で「バックアップの設定を引き継ぐ」です。「新しいURLをデータベースに保存」か「wp-config.php に記入する値を確認」を選ぶと、2つのアドレスを入力できます。確認用URLは隔離起動時だけ使います。確認用ポートの候補は、復元サーバーで8181〜8199のうち最初に空いている番号です。

確認用管理者の作成は初期状態でオフです。有効にした場合は確認用コピーにだけ作成します。運用へ移すときは完了画面に表示されるDBを使います。運用向けDBにURLを反映する場合、または確認用管理者を作成する場合、分離した運用向けDBを所有者専用領域に出力します。SQLiteは `migration-db/site.sqlite`、MySQL／MariaDBは `migration-db/site.sql` です。ユーザーが含まれていない世代から移行する場合は、運用開始前に移行先で管理者を用意します。

### 独立画面を起動する

状態フォルダーは所有者だけの`0700`で事前に作ります。root では実行できません。復元用のPHP CLIではシグナル拡張（pcntl）を有効にしてください。

```bash
php recover-web.php start --state-dir <private-dir> --port 8765 --age dependencies/age/age --direct-r2-connection-file <0600-file> --mysql-connections <0600-json>
```

WordPressプラグインでは、取得済み暗号文の場所を`wp-config.php`の定数`WRB_RESTORE_LOCAL_REPOSITORY`と`WRB_RESTORE_LOCAL_UNIT`で指定できます。独立画面で取得済み暗号文を使う場合は、`--direct-r2-connection-file`の代わりに`--repository <dir> --unit <64-hex>`を指定します。MySQL／MariaDBを使わない場合、`--mysql-connections`は不要です。

R2接続情報を復元画面で指定する場合は、起動時の`--direct-r2-connection-file`を省略できます。認証後、WordPressのバックアップ設定から取得したJSONのファイルを選ぶか、内容を全文貼り付けます。入力方法や内容を変えると、取得した一覧と検査結果が取り消されます。「バックアップ一覧を取得」を押して取得結果を確認し、別にage秘密鍵ファイルを選んでください。接続情報も秘密情報です。所有者だけが読める場所に保管し、WordPressの復元画面では、ループバック接続を除き、接続情報や秘密鍵などを送信する前にHTTPSで開きます。独立画面はローカル接続またはSSHトンネルで使用します。接続内容は事前検査と開始時の一致を確認し、復元ワーカーにはメモリー経由で渡します。画面を閉じたり復元を開始した後は入力し直してください。一覧では保存記録を確認し、「保存物は未照合」と表示します。事前検査では選択した目録を検証し、復元時には必要な保存物を照合します。

端末に表示された有効化コードを画面へ入力します。コードは10分間・一回限りで、失敗5回で失効します。起動出力を保存する構成では、管理者が指定した非公開ログを確認します。状態フォルダーの `web/token.json` にはコードの照合値だけを保存します。有効化画面には、起動時に指定した状態フォルダーを使って再発行する手順を表示します。

```bash
php recover-web.php issue --state-dir <private-dir>
```

```bash
php recover-web.php stop-job --state-dir <private-dir>
```

```bash
php recover-web.php stop-site --state-dir <private-dir>
```

待受は`127.0.0.1`だけで、Host・Originの完全一致を要求し、転送ヘッダー付きの要求を拒否します。別のPCからは同じポート番号のSSHトンネルで接続します。

開始の権限は開始時に消費し、無操作30分・最長8時間で失効します。実行中の進捗確認と停止は失効後も続けられ、終了の30分後に権限が失効します。画面を閉じても実行中の復元は続きます。

### MySQL／MariaDBの接続セット

専用サーバーと空のDB、アカウントを管理者が準備し、`0600`のJSONで登録します。ブラウザーから接続先は指定できません。手順とSQLのひな形は画面の「準備手順」にあります。

```json
{"version":1,"connections":[{"id":"local-db","label":"専用DB","workspace":"/path/to/workspace","socket":"/path/to/workspace/mysql.sock","mysql":"/path/to/mysql","mysqldump":"/path/to/mysqldump","database":"wrb_test_example","inspector":{"user":"root","password":""},"importer":{"user":"wrb_import","password":"..."},"runner":{"user":"wrb_run","password":"..."}}]}
```

`database`と3つのアカウントは省略でき、その場合は画面の詳細欄で入力します。原本用DBの取込アカウントと、`<DB名>_run`の起動用アカウントは別にし、それぞれのDBだけに権限を限定します。ソケットは作業領域内に置き、`.wrb-synthetic-mysql`の印と`event_scheduler=DISABLED`が必要です。

ビュー、トリガー、ルーチン、イベントがあるDBは、所有者を保ったまま別アカウントへ複製できないため、原本の復元・照合までで停止します。

### 運用URLの扱いと動作確認

- **バックアップの設定を引き継ぐ**。復元原本の設定ファイルとDBをそのまま保管します。
- **新しいURLをデータベースに保存**。元と同じ配置で使う単一サイトが対象です。確認済みの元URLと指定した別名を対象に、運用向けの別コピーで置換し、`home`（サイトアドレス）と `siteurl`（WordPress アドレス）を更新します。元のDBの値や設定ファイルの記述が事前確認の前提と合わない場合は、書き換えずに原本を保持します。
- **wp-config.php に記入する値を確認**。移行先に設定する `WP_HOME` と `WP_SITEURL` を完了画面に表示します。オリジン（HTTP／HTTPS・ホスト名・ポートの組）が同じであれば、WordPress アドレスにサイトアドレス配下のパスも指定できます。DB、本文と設定ファイルの書き換えは行いません。サブディレクトリを選んだ場合は、移行先で本体の配置とサイト入口の `index.php` の読み込み先も設定してください。[WordPress公式手順](https://developer.wordpress.org/advanced-administration/server/wordpress-in-directory/)を参照してください。`wp-config.php` の定数を定義すると、WordPressではDBの値より優先されます。
- **動作確認用URL**：隔離サーバーの待受 `http://127.0.0.1:<port>` です。DBへは保存しません。確認中の応答では、確認用コピーのURLを確認用URLへ読み替えます。運用先URLに接続したり、DNSやHTTPSを設定したりすることはありません。

開始前に表示する元のURLは、バックアップの記録に含まれる値です。元DBの `home`・`siteurl` と、保存されていた `wp-config.php` の定数の記述は、原本の照合後に確認します。個人情報除外などで保存されていない設定ファイルの値や、動的に決まる値は確認できません。

起動コピーには隔離用プラグインが入っています。公開運用へ移す作業は別の手作業です。

### 対応するサイト構成

通常の単一サイトだけに対応します。`home`と`siteurl`が異なる構成（サブディレクトリなど）とマルチサイトは、原本の復元と照合の後で起動準備だけを停止し、理由を表示します。原本は保持します。

旧`wp-config.php`の`WP_CONTENT_URL`や`UPLOADS`などの独自の配置先は引き継がず、検出した定数名を表示します。テーマやプラグインのファイルに直書きされたURLは書き換えません。`wp_posts.guid`も他の値と同様に置換します。公開済みフィードを持つサイトを公開運用へ移す場合は、GUIDの扱いを別に判断してください。

### 失敗したとき

DB取込に失敗したDBへは再取込しません。新しい空のDBと新しい復元名でやり直します。失敗先の削除は画面にはありません。起動準備だけが失敗した場合、SQLiteは原本から起動段階だけをやり直せます。MySQL／MariaDBの起動用DBは再利用しません。
